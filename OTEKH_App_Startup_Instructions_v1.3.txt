PURPOSE

This file is the standing instruction set for beginning any new OTEKH application project.

When this file and the Otekh_App_Shell package are uploaded together, treat the Shell as the authoritative visual and interface system for the new application.

Do not redesign, reinterpret, replace, simplify, darken, lighten, or otherwise alter the OTEKH design system unless the user explicitly asks to change the Shell itself.

FIRST RESPONSE

After reading this file and the uploaded Shell, begin by asking:

“What are we building?”

Do not begin coding immediately.
Do not generate a generic app concept.
Do not invent features, workflows, logos, colours, fonts, icons, or branding.

PLATFORM REQUIREMENT

OTEKH applications come in two shapes:

1. UNIVERSAL DESKTOP APPS — the default. Built for:
   - macOS
   - Linux

   Windows is not a target platform unless the user explicitly changes this requirement for a specific project.

   Every universal app must be planned, structured, tested, documented, and packaged for both macOS and Linux from the beginning.

   This means:
   - use cross-platform frameworks and libraries
   - confirm that the selected technical stack supports both macOS and Linux before development begins
   - avoid macOS-only implementation choices unless there is a Linux equivalent
   - avoid Linux-only implementation choices unless there is a macOS equivalent
   - use platform-aware file paths and native file pickers
   - support Command shortcuts on macOS and Control shortcuts on Linux
   - package fonts and approved OTEKH assets with the application
   - document separate macOS and Linux install, run, build, and packaging steps where they differ
   - test window sizing, scaling, keyboard access, file operations, drag-and-drop, and offline behaviour on both platforms
   - do not provide Windows instructions, installers, paths, or compatibility work unless explicitly requested

2. RASPBERRY PI LOCAL APPS — single-machine apps that run on a Pi 4/5 with a local display: sensor stations, kiosks, field devices, lab instruments. These are Linux apps first (everything in LINUX.md applies) but may be Pi-only when they depend on GPIO/I2C hardware.

   For Pi local apps:
   - the reference stack is Python + CustomTkinter — see RASPBERRY_PI.md and Otekh_App_Shell/docs/TKINTER.md
   - use the Shell's Tkinter toolkit: tokens/otekh_tokens.py, tkinter/otekh_shell.py, starter/starter-shell-tkinter.py
   - use the TTF fonts in install_fonts/*/ttf/ — Tkinter cannot load WOFF2
   - GPIO on Pi 5 uses rpi-lgpio (never RPi.GPIO); I2C uses adafruit-circuitpython-* libraries
   - hardware failures surface as empty/None readings, never crashes
   - ship install/update/uninstall scripts and a .desktop entry so the app behaves like a native Pi application

CODE REQUIREMENTS

- Apps must be written in a human-readable programming language — never delivered as binary or machine-language-only artifacts.
- Code must be clear and maintainable enough that a human user can make changes without agent assistance: sensible structure, meaningful names, comments where needed, no obfuscation or opaque generated-only code.
- Follow the OTEKH commenting standards (agent.md / DEVIN.md): file headers declaring PROVIDES/CONSUMES, commented imports, section banners, cross-file call-site notes, WHY-not-WHAT comments, and no stale comments — written as you code, never deferred.

PRIVACY AND SECURITY — NO-COOKIE ETHICS PROTOCOL

OTEKH labs is not in the business of surveillance. Every web app is designed to function properly and securely without cookie tracking of any kind:

- NO COOKIES REQUIRED — the app must work fully with cookies blocked or cleared. Authentication rides on a session token sent as a request header (Authorization: Bearer or X-Session-Token), held client-side in memory or per-tab sessionStorage.
- NO TRACKING — no analytics, advertising, fingerprinting, third-party identifiers, or cross-site anything. No consent banners either: there is nothing to consent to.
- OPTIONAL SESSION COOKIE — at most one first-party HttpOnly SameSite=Lax cookie may carry the same session token as a fallback for full-page loads; it is never required and never holds profile data.
- AUTH FILE — bootstrap credentials live in a separate gitignored auth file (username=/password=), seeded into the user store at startup; passwords are salted+hashed in the store.
- MASKED PASSWORDS — every password field is masked; passwords never appear in logs, URLs, or error messages.
- ROLE GATING — admin features are hidden from other roles in the UI and re-enforced on the server; hiding alone is not authorization.

Full rules and the shared auth/admin UI patterns are in Otekh_App_Shell/docs/SECURITY_PRIVACY.md.

DISCOVERY PHASE

Work conversationally with the user to define the application before building it.

Help identify:

- the purpose of the app
- who will use it
- what files, data, devices, or services it works with
- the main tasks users need to perform
- the major screens or work areas
- the key controls and interactions
- required offline, local-network, server, or web behaviour
- what belongs in the first working version
- what can wait until later versions

Keep this phase practical and collaborative.
Do not turn it into a large formal requirements process unless the user asks.

LAYOUT EXPLORATION

Before coding, present a small number of layout options in plain text.

Use simple text diagrams, labelled regions, or compact wireframes.

Example:

OPTION A — TRACK VIEW

┌─────────────────────────────────────────────────────────────┐
│ OTEKH / APP NAME                        STATUS / FILE / MENU │
├──────────────┬───────────────────────────────┬──────────────┤
│ DATA / LIST  │ PRIMARY WORK AREA             │ INSPECTOR    │
│              │                               │              │
│              │                               │              │
├──────────────┴───────────────────────────────┴──────────────┤
│ PLAYBACK / PROGRESS / CONNECTION / SAVE STATE              │
└─────────────────────────────────────────────────────────────┘

Present two or three meaningful alternatives when useful.

For each option, briefly explain:

- what the main working area is
- where navigation belongs
- where controls and settings belong
- what expands, collapses, or resizes
- why the layout suits the task

Do not use image generation as the main design method.
Simple sketches or interface mockups may be used only to help decide structure.
Once the basic layout is chosen, move toward a real working interface.

APPROVAL POINT

Before coding, confirm the agreed first-version foundation in a compact summary:

- app name
- purpose
- first-version features
- selected layout
- major screens or panels
- input files or data
- expected platform: macOS and Linux, or Raspberry Pi OS for local apps
- anything intentionally deferred

Then proceed.

PROJECT SETUP

Provide exact Terminal commands for creating the application folder.

Always begin Terminal instructions with the folder-location step.
Never assume the user is already in the correct directory.

Example:

cd ~/Desktop
mkdir -p OTEKH_New_App
cd OTEKH_New_App

The user will place the OTEKH Shell into the project.

Recommended structure:

OTEKH_New_App/
├── shell/
│   ├── Assets/
│   ├── components/
│   ├── docs/
│   ├── install_fonts/
│   ├── tkinter/
│   ├── Log/
│   ├── starter/
│   ├── tokens/
│   └── OTEKH Application Style Guide
├── src/
├── data/
├── docs/
└── README.md

Use the actual folder names found in the uploaded Shell.
Do not invent replacement assets when approved assets already exist.

For Tkinter apps, copy tokens/otekh_tokens.py and tkinter/otekh_shell.py into the project's source tree (or import them in place) so the app reads token values directly rather than copying hex codes.

READING THE SHELL

Inspect and use the uploaded Shell before creating the first version.

Treat these as sources of truth:

- design tokens (design-tokens.json, otekh-tokens.css, otekh-theme.ts, otekh_tokens.py)
- CSS components (web) and the Tkinter shell toolkit (otekh_shell.py)
- starter shells (starter-shell.html, starter-shell-tkinter.py)
- official logos
- official icons
- typography
- spacing
- colour roles
- accessibility rules
- component specifications
- security and privacy rules (docs/SECURITY_PRIVACY.md — no-cookie protocol, auth, roles)
- QA checklist
- changelog

Use the exact assets and values supplied.

Do not substitute visually similar colours.
Do not recreate the OTEKH logo.
Do not invent app icons when an approved icon exists.
Do not replace Bai Jamjuree or Inter unless explicitly instructed.
Do not add shadows, gradients, faux depth, glossy controls, or decorative effects that conflict with the Shell.

Font note: web/Electron apps use the WOFF2 files in install_fonts/; Tkinter apps must use the TTF builds in install_fonts/*/ttf/ and install them before the Tk root is created (otekh_shell.ensure_fonts() does this). Keep licence files with distributed fonts in both cases.

BUILD PHASE

Create the smallest useful working version first.

The first version should:

- launch successfully on its target platforms
- use the OTEKH Shell
- show the agreed layout
- implement the core workflow
- use real or representative user data where available
- make system state visible
- be easy to revise

Do not attempt to complete the entire application in one pass.

Build in understandable pieces.

Suggested sequence:

1. application shell and primary layout (starter-shell.html or starter-shell-tkinter.py)
2. file or data loading
3. primary work view
4. core controls and interactions
5. inspectors, metadata, or settings
6. saving, exporting, or reporting
7. accessibility and error states
8. packaging and release for the target platforms

ITERATION

After each working version:

- provide the exact command to run it
- provide macOS, Linux, and/or Raspberry Pi OS commands separately where they differ
- ask the user to test the real interface
- revise based on what they see and experience
- preserve approved parts
- change only what is being discussed
- add features gradually

The process is:

Build → Run → Test → Discuss → Revise → Add

Do not restart the design from scratch after every criticism.
Do not replace the agreed layout with a generic alternative.
Do not reopen settled style-guide decisions unless the user asks.

WORKING PRINCIPLES

1. The Shell is authoritative.
2. The app’s purpose determines the layout.
3. Existing approved work is preserved.
4. Functionality is built in small testable pieces.
5. The user can change direction at any time.
6. New product-specific components may extend the Shell, but they must still follow its tokens, geometry, typography, accessibility, and interaction rules.
7. When uncertain, ask about the application’s behaviour rather than inventing a new visual language.
8. Prefer the real working interface over polished speculative mockups.
9. Keep the application local and offline-capable where required.
10. Continue iterating until the user is satisfied.
11. Build universally for macOS and Linux from the beginning — or explicitly for Raspberry Pi OS when the app is a Pi local app.
12. Windows is excluded unless the user explicitly requests it.
13. Code stays human-readable and human-maintainable, commented to the OTEKH commenting standards as it is written.
14. No cookie tracking — sessions use header tokens; the app works fully with cookies disabled (docs/SECURITY_PRIVACY.md).

Universal apps are built for macOS and Linux; Raspberry Pi local apps use the Shell's Tkinter toolkit. All apps follow the no-cookie ethics protocol — no tracking of any kind. What are we building?”
